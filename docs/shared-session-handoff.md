# 다른 PC 작업 인계

확인일: 2026-09-21
출처: https://chatgpt.com/s/cx_6aaffbbb64c88191b77cdd06e43f36f4
공유 작업 제목: 호텔 정보 기반 광고 생성 계획

## 이 문서의 범위

공유 대화 마지막 응답까지 읽고 최신 결정과 진행 상태를 정리했다. 공유 대화에서 보고한 완료와 현재 PC에서 확인한 파일을 구별한다. 다른 PC의 원본 파일을 가져오거나 그곳의 테스트를 재실행한 것은 아니다. 과거 모델 가격 및 잔액은 현재 조회 결과가 아니다.

## 프로젝트와 최신 방향

- AI 엔지니어 부트캠프의 숙박 소상공인용 광고 이미지 서비스. 사용자는 모델 파트 담당이며 프런트엔드·백엔드·DB는 다른 팀원이 담당한다.
- V2 흐름: 대화로 기획서 수집 → 기획서 확정 → 같은 사진과 기획서로 A/B/C 광고 생성 → 사용자 선택.
- 초기 외부 채팅 API 중심 제안보다 이후의 vLLM 도입 방향을 우선한다.
- 예정 구조: React → FastAPI → gRPC 모델 서비스 → 내부 OpenAI 호환 HTTP API → vLLM 채팅 모델.
- 이미지 생성은 기존 OpenAI 이미지 API를 활용하고 모델 서버에서 한글 문구를 합성한다.
- 사용자가 확인한 실행 환경은 이미 생성된 GCP Linux VM + NVIDIA L4. VS Code SSH로 접속할 예정이며, 접속 정보를 여기 공유할 필요는 없다.
- Qwen3-8B non-thinking은 초기 검증 후보다. 실제 VM 드라이버·가용 VRAM·모델 로딩·실행 옵션은 미검증이다.

## 백엔드와 합의한 요구사항

- 채팅 Agent는 상태를 보관하지 않는다. 임시 대화·기획서는 React에서 관리하여 요청마다 전달하고 최종 확정 시 DB에 저장한다. 사진은 업로드 시 저장한다.
- 질문 순서: 숙소 유형 → 숙소 정보 → 매력·사진 → 광고 대상 → 분위기·색상 → 광고 문구. 유효하게 완료된 단계는 건너뛴다.
- 한 메시지의 여러 필드 추출, 모호하거나 무관한 답변 재질문, 완성 전 정정·삭제·재확인을 처리한다.
- 숙소 유형: `hotel`, `motel`, `resort`, `pension`, `other`. 그 외 유형은 `other`와 `lodging_type_detail`로 표현한다.
- 주요 기획서 필드: `lodging_type`, `lodging_type_detail`, `lodging_name`, `location`, `selling_points`, `target_audience`, `mood`, `color_preference`, `ad_copy`.
- 광고 문구는 직접 입력하거나 AI 후보 최대 3개 중 선택한다.
- `answer_status`에 `not_applicable`을 포함하며 `state_revision`, `resume_step`, `fields_to_reconfirm`을 사용한다.
- 최근 최대 12개 메시지, 최대 8,000토큰을 전달한다. 시스템 지시·기획서·출력 토큰까지 포함한 실제 모델 문맥 한도는 별도 검증해야 한다.
- 완료된 기획서는 읽기 전용이다. 완성 후 기획서 수정 및 선택 이미지 직접 편집은 V2 범위 밖이다.
- A/B/C는 `GenerateDraft`로 독립 호출한다. A는 객실·시설, B는 분위기·경험, C는 확인된 장점·메시지를 강조한다. 제공되지 않은 혜택을 생성하지 않는다.
- 최종 이미지는 한글 합성이 완료된 1024×1024, 1:1 PNG다.
- 입력: JPEG, PNG, 정적 WebP. 업로드 파일 최대 25MiB(26,214,400 bytes), 절대 상한 60MP.
- FastAPI가 EXIF 방향·색상 모드를 정규화하고 20MP 초과 60MP 이하 이미지를 비율 유지하여 20MP 이하로 축소한다. 원본은 별도 보존한다.
- 60MP 초과·손상·형식 불일치·애니메이션 WebP는 거부한다. 모델 서버도 전달받은 bytes·MIME·크기를 검증한다.
- 후속 계약 제안은 백엔드가 추가 의견 없이 승인했다. 다만 정규화 후 bytes 제한, 사진 이벤트, revision, 삭제 및 재확인 등의 정확한 wire 규칙은 다른 PC의 최종 계약·proto 원본으로 확인해야 한다.
- 초기 timeout: 채팅 30초, 이미지 180초. 구조화 오류는 `reason`, `retryable`, `request_id`를 제공한다.
- `generation_round`, `is_regeneration`을 사용한다. 사용자 다시 생성은 세션당 성공 기준 1회다.
- 시스템 재시도·부분 실패는 사용자 횟수를 차감하지 않는다. 부분 성공 결과를 재사용하며 세 장 모두 완료되기 전 새 회차를 비활성화한다. 횟수와 저장 성공 판정은 백엔드 책임이다.

## 다른 PC에서 완료했다고 보고한 산출물

- `docs/v2-model-design-reply.md`: 설계 회신 및 백엔드 결정 반영.
- `docs/v2-model-selection-report.html`: 당시 API 모델·예산 비교 보고서. 이후 vLLM 도입 방향을 함께 고려해야 한다.
- `docs/v2-gpu-environment.md`, `scripts/check_gpu_environment.py`: 환경 안내 및 사용자가 VM에서 실행할 점검 스크립트.
- 계약 문서, 요청·응답 JSON: 채팅 22개·이미지 6개·오류 8개 사례. 정확한 파일명은 공유 대화 본문에서 확인하지 못했다.
- `proto/hotel_ad_v2.proto`: 최종 V2 계약, `ProcessTurn`, `GenerateDraft`, `HealthCheck`.
- `requirements-v2-contract.txt`, `examples/v2_client.py`, JSON 변환 코드, Stub 생성 안내, 계약 테스트, 백엔드 전달 ZIP.
- 해당 대화의 검증 보고: proto 컴파일 성공, 로컬 가짜 gRPC 서버 테스트 7개 통과. 현재 PC에서 재검증한 결과는 아니다.
- 실제 V2 모델 서버 및 vLLM 연결은 아직 미구현이라고 마지막 응답에 명시됐다.

## 현재 PC에서 확인한 상태

프로젝트 파일 목록에는 V1 `grpc_server.py`, `image_service.py`, `proto/hotel_ad_image.proto`, `proto/vllm_engine.proto`, Docker 구성 및 V1 테스트가 있다. 위 V2 산출물은 이 인계 문서를 작성하기 전 파일 목록에 없었다.

따라서 대화 맥락은 인계했지만 최종 proto·클라이언트·계약 자료의 원본 파일 동기화는 아직 필요하다. 공유 대화의 요약을 바탕으로 최종 계약을 임의 재작성하지 않는다.

## 예산 기록

사용자가 당시 밝힌 팀 OpenAI 크레딧은 총 $30, 사용액 $1.06, 잔액 $28.94였다. 현재 잔액은 미조회다. GPU 비용은 별도이며, 이전 API 모델 후보와 단가는 역사적 제안이다. 이번 인계 과정에서는 유료 모델 호출을 하지 않았다.

## 다음 작업 순서

1. 다른 PC의 최종 계약·proto·예제·테스트 원본을 저장소 동기화 또는 전달 ZIP으로 확보하고 현재 파일과 비교한다.
2. 계약에 맞춘 V2 서버 골격과 가짜 응답 모드를 구현한다. V1을 유지하고 입력 검증 및 구조화 오류를 포함한다.
3. GCP L4에서 사용자가 점검 스크립트를 실행하여 실제 환경을 확인하고 vLLM/Qwen 후보를 검증한다.
4. vLLM 정보 추출과 코드 기반 기획서 검증·단계 이동·재확인·문구 선택을 연결한다.
5. A/B/C 이미지 생성, 정확한 한글 합성, 회차별 레이아웃을 구현한다.
6. 실패·재시도·부분 성공·전체 사용자 흐름을 통합 검증하고 비용·지연을 기록한다.
7. Docker·환경변수·운영 문서 및 발표 시연을 준비한다.

이 순서는 공유 대화의 마지막 진행 상태를 옮긴 것이다. 이번 요청으로 후속 구현 전체가 완료된 것은 아니다.
